# Security implementation notes

The security definition is in [app-definition/security.md](app-definition/security.md). Codex executes requests from approved HTTPS/loopback origins only after checking native sign-in, effective isolation settings and a private ephemeral thread. The installed official client handles all provider authentication/inference. WDC never reads its credential files or implements a token exchange. Claude uses its native CLI in a verified Restricted profile; explicit App tools/Workspace add only the private WDC adapter. Incompatible clients/policies and unsupported modes fail closed. Details and file limits are in [native execution](native-execution.md).

## Implemented boundaries

- IPv4 loopback binding, exact Host/remote-address checks, allowlisted browser origins, authenticated API access. GET/HEAD navigation outside `/api` on exactly `localhost:<listening port>` redirects to `127.0.0.1` on the same port; it serves no data on the alias. Public static assets and CORS preflight expose no private state.
- Private launch fragment exchanged for independent 12-hour session and CSRF tokens. The panel keeps the session ID in origin-scoped browser storage and sends an explicit X-Bridge-Session header, omitting cookies; CSRF token plus exact Origin protect changes. This isolates separate loopback ports and prevents ambient cookies from reaching unrelated local services. No third-party assets, inline scripts, framing, or referrers. The root key is never sent to paired apps.
- User-created, single-use invitations bind app ID, origin, app user and installation device. They transfer the runner public-key pin through the authenticated control panel. Pending invitations can be listed and revoked by an authenticated panel session with its CSRF token (revocation also requires exact Origin). Listing never returns the invitation token or verifier; only the creating tab retains a copy in session storage. The invitation secret is stored as a SHA-256 verifier; app pairings store public keys, never app private keys. Runner signing and root control keys are separate private local files.
- Ephemeral ECDH P-256 and HKDF-SHA256 establish direction-specific AES-256-GCM keys after verifying a signed, challenged handshake against the trusted pin. Every request and response is separately ECDSA P-256/SHA-256 signed. Nonces, timestamps, channel/request bindings, stream sequence/hash chains and authenticated end frames prevent accepting substituted, replayed, reordered or falsely completed output. Verification precedes SDK delivery. No unsigned/bearer fallback exists. Negotiated bounded fragments retain every signature and stream-chain binding.
- Separate per-tab leases, checked by the runner. Lease release/expiry, pause, revoke, cancellation and timeout affect only the relevant scopes. Closing the control panel does not cancel other apps.
- One durable JSON state store, single-writer OS file lock, write+fsync+rename before state publication. A failed save does not publish a live mutation. Corrupt/unknown state is preserved and refused. A crash interrupts pending jobs rather than replaying them.
- Jobs are pairing-scoped. Prompt/permission fields cannot inject commands, paths, provider options or API keys: unrecognized fields are rejected. Native requests default to Restricted; App tools dispatch registered callbacks whose app owns authorization; Workspace folder access uses remembered grants and operation-specific write approvals. Separately configured Commands mode requires exact versioned grants and explicit OS-account consent. Unavailable native modes and provider eligibility have no execution bypass.
- Terminal prompts and command inputs are erased. Request history defaults on, including for existing installations. The owner can disable it globally or override it per connection (global/keep/don’t keep); connection overrides win in both directions. Disabling confirms and deletes stored finished records in the affected scope, including routing refusals. Opted-out terminal jobs never appear in panel state or durable job state. Output and artifacts are held only in memory for delivery, then purged; uncollected results expire one minute after finishing. Successful signed result responses (stream, GET, lookup, duplicate submission or cancellation) collect the result; artifact results wait for every file byte. Failed signed writes leave the result available until the same fixed deadline. Minimal hashed idempotency receipts remain durable and prevent replay after deletion/restart. Open sessions retain their execution context until ended; their closure notices are transient. History deletion removes retained terminal job content. Logs contain runner-level startup/errors, not request bodies or credentials. State, key, metadata and log files use restrictive Unix modes; state directories use 0700. Windows applies a protected current-user/SYSTEM DACL with private inheritance. Local reads reject links, special files and size overruns; atomic writes use unique private temporary files and Unix directory fsync. The launcher authenticates runtime challenge proofs before disclosing its control key.

## Limits and remaining security work

This is one OS user's runner, not a multi-tenant service or a defense against malware already running as that user. A local process with equivalent filesystem rights can read the control key or modify the binary. App account binding relies on the integrating app's authenticated account claim and the user's invitation confirmation; there is no remote identity-attestation service.

An app's signing key is authoritative for that pairing and must not be shared between accounts. A backend must not use one user's pairing to fulfill other users' requests. The bridge does not infer user identities from prompts. Native account metadata is checked at dispatch and each turn; an installation-scoped fingerprint is pinned privately to the pairing. A changed account requires reconnecting. API-key-only authentication is rejected.

Browser heartbeats are best effort. Closing, losing network, sleeping or suspending a tab can cancel requests after the documented grace period. The runner does not promise immediate close detection. A malicious app can continue renewing its own lease, so app SDK integration and account scoping must be reviewed. The optional self-hosted relay uses outbound HTTPS polling and backend-owned leases; see [relay security and recovery](relay.md). Backend authorization never grants local permissions.

Local unauthenticated clients can fetch the static login shell; all private information and mutations require authentication. The listener can still be subjected to local denial of service. This is not an Internet-exposed service. Serving behind a reverse proxy is unsupported.

Cross-platform CI now passes Unix storage, Windows DACL/junction, process lifecycle, Windows install/removal and Linux tray checks. Real Windows/Linux native-provider sandboxes and clean-machine download/browser behavior remain early-user testing work. Atomic rename prevents torn JSON; there is no tested guarantee against every form of power loss or storage failure. No encrypted history/key vault is implemented; the OS account protects local files. SDK app keys are non-extractable browser CryptoKeys; keep them in account-scoped memory or IndexedDB structured cloning. Non-extractable does not stop scripts executing in that origin from using the key.

Codex controls, ephemeral context, tool/configuration isolation, schema validation and file boundaries are described in [native execution](native-execution.md). App tools require registered callbacks and compatible native controls. Workspace additionally requires explicit folder grants. Hosted/commercial Codex eligibility, organization-managed Claude policies and WSL remain explicit limits. Native image cache copies are managed by Codex, not erased by WDC history deletion.

## Trust and cryptographic limits

The requesting browser verifies and decrypts the content, so the website and its scripts can read it. Signing authenticates origin of bytes; encryption protects transport content. This is not end-to-end secrecy from the requesting app, a defense against its XSS/extensions, or remote attestation of an unmodified runner. A compromised trusted invitation transfer can substitute a different identity. The user must launch their installed app through its private control link, rather than trusting an arbitrary site claiming to be its control panel.

The SDK never receives the runner private key. The runner never receives the app private key. A server-side private key must not be embedded in JavaScript; this direct browser integration authenticates a separate per-pairing browser key, not the website's backend. Adding backend attestation would require its own authorized protocol.

Old unsigned pairings are revoked during migration. Missing/replaced runner identity keys revoke existing pairings; corrupt identity files stop startup. SDK pins never rotate automatically. Re-pair after losing keys, changing runner address or clearing app storage. Ephemeral channel keys exist only in memory. HTTP metadata and timing remain visible; local HTTP browser restrictions still apply. Control-session transport retains its separate local-only session/CSRF model. Same-origin script compromise can use that session; bundled assets, text-only rendering and strict CSP remain part of the boundary.

This small application protocol uses [standard WebCrypto primitives](https://www.w3.org/TR/webcrypto/) and Go's [crypto/ecdh](https://pkg.go.dev/crypto/ecdh), [crypto/ecdsa](https://pkg.go.dev/crypto/ecdsa), [crypto/hkdf](https://pkg.go.dev/crypto/hkdf) and AES-GCM implementations. Automated tests cover fake runner pins, handshake substitution, signature/tag tampering, replay, wrong app keys, stream removal/reordering/duplication, truncation/reconnect and restart/key reset. These tests do not replace independent protocol/cryptographic review; none has been performed. Wire formats and bounds are in [protocol.md](protocol.md).

## Configured command boundary

The startup `config.yaml` policy defaults to a disabled web command editor. It is parsed strictly and is never written through HTTP. Only explicitly enabled, authenticated control sessions may write the separate managed action store; file-defined actions remain read-only. Paired app requests cannot tunnel control routes, choose executable paths, modify arguments schemas or grant themselves access. A command edit invalidates existing definition-hash grants and cancels affected live jobs.

Configured commands run with OS-account rights, not a Restricted sandbox. Direct argument vectors and validated inputs avoid implicit shell interpolation, but an allowed program can still read/write files, access the network or launch other programs according to the user's permissions. This privilege is acknowledged separately when granting a website access. Environment filtering and private working directories reduce accidental inheritance; they do not isolate arbitrary programs. Lifecycle controls and their Unix crash/detachment and Windows runtime-test limitations are documented in [commands.md](commands.md). No independent security review has been performed.


The OS launch URL contains only an origin, public requesting key and short-lived challenge. A root-authenticated local launcher enables rendezvous; browser Origin, signatures and nonce checks bind the actual request. WDC approval is still mandatory. Invitation replies are signed/encrypted and invitations can be claimed only by the original key. This does not attest the installation against malicious same-user processes.

App tool callbacks are claimed once for their exact pairing/account/lease. WDC never replays an uncertain callback; applications must deduplicate backend mutations using its call ID. Tool-result JSON and attachments are untrusted. Folder access uses identity-checked rooted operations, rejects escaping symlinks and protects WDC/provider configuration roots. Write approvals bind the preview content hash and are rechecked before replacement. Permissions cannot authorize a general shell; configured executables retain separate Commands consent and OS-account permissions.

## Application updates

Community releases are manual-update builds: macOS signatures are ad hoc, Windows binaries are unsigned, and the complete download checksum list is authenticated by the committed Ed25519 community key. They cannot enable the official updater or contact its service. This authenticates release bytes without claiming an OS-trusted publisher.

Official releases use a separate pinned Ed25519 release key, version/target/size/hash checks, Windows Authenticode verification and macOS Sparkle/Apple signature validation. Websites cannot choose feeds, replace trusted keys or invoke owner update routes. Automatic installation drains work before stopping the desktop app; explicit owner cancellation is separate. Updates preserve pairing identities and replay receipts, never restore stale state snapshots, and use bounded private staging. Development builds cannot silently replace themselves with official downloads. The two-minute control-panel handoff is local, private and single-use. See [updates](updates.md), [privacy](../PRIVACY.md) and [release/key handling](releases.md).

## Optional relay

The [relay guide](relay.md) defines pairing, signed connection/deadline binding, streaming integrity, retention and project ownership. Desktop administration remains loopback-only. The relay and authenticated backend are trusted with plaintext requested content; native credentials and desktop private keys stay local.

A shared deployment binds each connection and enrollment to a persisted project identity. A project's credential cannot use or revoke another project's connections, including when both use the same account ID. Operator registration/key rotation/revocation use a separate admin credential that cannot submit inference. Project identities are immutable, credential hashes are persisted, and revocation cancels affected exchanges and connectors. Projects share operator trust and deployment limits; see the relay guide for provisioning and existing-state handling.

Relay app links carry a short-lived single-use pairing code and relay origin, or an existing opaque connection ID for opening settings. They never carry project credentials, provider keys, a full desktop invitation or an administration key. Inspection displays the exact project, website and account; local approval remains mandatory. Links cannot select models, enable automatic execution or grant folders/commands. New workflow migration aliases can copy only the same pairing's existing local route and never overwrite an already-declared choice. Partial native options resolve locally and the final program/model/reasoning remain pinned in the existing execution plan. The direct requesting-key launch flow is unchanged.

## Named AI programs and custom harnesses

AI program definitions are local session/CSRF-protected configuration. Websites cannot add or edit them. Stable IDs keep route selections independent of display names; configuration hashes pin execution and end affected work on executable/profile/argument/type changes. Native account fingerprints remain bound per connection and program across edits. Removing a used entry never selects a replacement automatically.

Custom harnesses use explicit per-connection, configuration-bound grants with the existing command OS permission model. Text, streaming and optional conversations do not imply native isolation. This interface rejects JSON schemas, files, images, app tools and workspace requests before dispatch. Accounts are verified only as far as the custom executable reports a truthful identity; absent identity is visibly unverified. Codex/Claude dedicated integrations still verify native sign-in and effective isolation for every selected entry. See [AI programs](ai-programs.md).
