# Connection file access (0.2.2)

File access is a saved, independent connection permission. It covers app-supplied images/documents and files returned by that app's jobs. Automatic execution, computer-folder grants and command/custom-program OS access remain separate. Generic file transport has no filename-extension allowlist.

New connections default to files off. Existing state loads with files off, without changing connection identities, keys, other grants or receipts. Apps can suggest `requestedPermissions: {files: true}` in direct pairing or relay enrollment. The desktop shows **Send and receive files**, checked according to that suggestion; the owner can uncheck it before Connect. Suggestions never grant access by themselves. Each connected card has a **Permissions** button and a summary of approval policy and file access. Its modal keeps **Run requests automatically**, **Send and receive files**, and folder grants in one draft. **Folder access**, the folder picker and **Back to Permissions** are views of the same modal; navigation never saves or discards edits. **Save changes** applies every changed permission in one owner-authenticated transaction, from either the overview or folder editor. Validation and persistence rejections leave saved grants unchanged. A definite validation rejection keeps the draft editable; a transport failure requires reconciliation as described below. **Cancel**, Close and backdrop dismissal offer **Keep editing** or **Discard changes** when dirty. Escape goes back from a subview and offers that choice at the overview. Clean dismissal needs no confirmation; saving disables editing and dismissal while the request is pending. Folder access in the card menu opens the same editor. File transfer and computer-folder access remain independent permissions; command access retains its own explicit review.

Permission drafts carry the connection's monotonic `permissionsRevision`. Every persisted permission change advances it, including changes from other windows, file/folder reviews, pause/revoke and command/program grants. Returning a grant to its original value still advances the revision. Names and routing preferences do not. Owner `PATCH /api/pairings/{id}` accepts `expectedPermissionsRevision` and a 64-hex `permissionSaveId`; stale drafts return `409 permissions_changed` before applying any setting. The modal freezes the stale draft and offers an explicit **Reload saved permissions** confirmation. It never silently restores an older folder grant.

The same transaction stores the last save ID and a private canonical payload hash. Exact retries return the current permissions without reapplying the write or revalidating old folder paths; reusing the ID with different changes returns `409 permission_save_conflict`. The receipt survives restart. Owner `GET /api/pairings/{id}` exposes the revision and last save ID, but never the payload hash. Remote app capabilities expose none of these owner recovery fields. Existing saved pairings need no migration.

If a Save acknowledgement is lost or unreadable, the modal checks this owner endpoint. A matching receipt and unchanged intended grants confirm success. A newer permission revision requires reloading; an unavailable or inconclusive read shows **Save not confirmed** and freezes editing. **Check saved permissions** only reads; **Retry save** explicitly resends the same immutable ID and payload. Closing an uncertain draft explains that changes may already be saved and that closing will not undo them. It never describes that outcome as unsaved or offers to discard an already applied permission change.

An existing connection can explicitly call `client.requestPermissions({files:true}, {signal})`. This creates a one-time desktop review, not an inference request. Approving saves file access for the connection; declining creates no upload or inference. Concurrent requests from the same lease reuse the pending review. Desktop review is authoritative for browser and backend-relay transports; an app request cannot approve itself. Preflight remains read-only and returns `files_not_granted` when an otherwise supported file operation needs approval. `fileTransfer` describes support, while `permissions().files` and `capabilities().pairing.files` describe the approved grant.

The desktop checks the grant on upload reservation, every upload chunk, file-bearing job admission, image generation/editing, file tool results, artifact creation and every output download chunk. File-enabled configured commands need the grant. A custom harness without the grant can still receive text prompts, but receives no WDC file manifest or output directory. Its separately approved OS account access is unchanged. Artifacts remain restricted to their producing pairing. The authenticated local owner can inspect their own job files independently.

Turning files off clears pending file uploads and cancels file-bearing live jobs. It closes continuing sessions that received files, including files returned by a callback; those cached contexts cannot continue as text-only sessions. Text-only scopes and bounded prompt context uploads remain live. Already shared files cannot be recalled. Regranting never resubmits inference. Receipt lookup/recovery still precedes new admission checks and never executes a consumed key again.

## Large text context

Apps must not use file uploads for ordinary large prompts. `client.uploadContext(text)` returns a tab-bound ID for NUL-free UTF-8 text, at most 128 KiB. Pass it as `contexts:[id]` to a standalone task or session message. It is appended to prompt text and never staged as a file, passed to a file manifest, or resolved by a file tool result. At most one context per turn is accepted. The upload class is fixed by its authenticated creation endpoint; changing a MIME label cannot convert a file into context. Ordinary inline requests retain the 40 KiB logical limit. Context uses the existing encrypted 24 KiB chunk channel and shared upload-memory/slot limits.

```js
const context = await client.uploadContext(savedHistory);
await client.run({prompt: 'Continue the conversation.', contexts: [context.id]});
await client.removeInput(context.id);
```

A text prompt can of course describe or contain text copied from a document. This permission controls WDC binary file transfer and file staging, not the meaning or origin of text an app supplies.

## Returning pixels to the chat AI

A tool callback may upload originals and return `client.toolResult(jsonResult, inputIds)`. This emits a small `{$wdc:'tool-result',result,inputs}` envelope. The desktop resolves only complete files from that callback's pairing and lease, validates their hashes and enforces file access. Hold the uploads until the owning execution is terminal. Result JSON remains subject to the ordinary 32 KiB callback limit; binary data travels through encrypted chunks.

Images become actual Claude MCP image content. Codex receives them through `turn/steer` bound to the exact active thread/turn, before its pending callback is released; JSON remains the tool result. This is a provider adapter workaround: in local tests the installed Codex acknowledged dynamic-tool image blocks while the model could not inspect them, but normal same-turn image inputs worked. Steering starts no new native turn, session or WDC job. Document tool results use bounded text representations; Claude's original PDF document blocks are available on normal turn inputs. The desktop binds file use to the parent job/session before returning content. Duplicate identical result acknowledgements remain idempotent even after upload cleanup; different results conflict. If the desktop explicitly rejects file references as invalid or ungranted, the SDK delivers the original JSON with a file-delivery warning instead of leaving the callback pending. It never reruns the handler or retries an uncertain acceptance.

Codex callbacks received during an outstanding RPC are queued in wire order and dispatched after its response is consumed. This prevents overlapping image callbacks from consuming each other's steering acknowledgements, and binds early callbacks only after `turn/start` returns its turn ID. The pending-event queue remains bounded; unknown server requests and mismatched response IDs are rejected.

After an application result is accepted, document/image conversion failures and rejected image steering retain its original JSON as a successful tool result. A separate `fileDelivery: {ok:false, code:'file_delivery_failed', ...}` text block states that the files could not be inspected and the operation must not be repeated automatically. No invalid media is forwarded. Permission, ownership, expired-scope and cancellation failures still stop delivery.

Capability markers are `filePermissionsVersion:1`, `textContextVersion:1` and `toolResultFilesVersion:1`. Pairing/launcher/relay capabilities advertise the file-permission review marker; new SDKs reject older peers before relying on it. Publish desktop/relay and SDK artifacts together before releasing apps that use these APIs. Publishing artifacts does not deploy relay or application servers, or replace a running desktop installation.
